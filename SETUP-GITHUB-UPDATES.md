# Deadlock Counter Advisor — first GitHub release setup

Repository: https://github.com/awkwardcarl/deadlockcounteradvisor

## What this version does

The v0.7 source is ready for an *installed Windows NSIS build* that can check GitHub Releases after startup, then offer **Download update** and **Install & restart** controls. Update downloads and installation require user approval. The app never forces a restart during a match. Existing manually entered game data remains local, and no Overwolf telemetry is enabled.

**Status:** Code and local logic tests are complete. No GitHub files or releases have been posted automatically, and the Windows installer has not been run/tested here.

## One-time repository upload

1. The repository must be **public** for unauthenticated community update checks; a private repository is not suitable for a free public app updater without giving out access credentials.
2. Install [Git for Windows](https://git-scm.com/download/win) if it is not already installed.
3. Extract this ZIP and run `Push-Source-to-GitHub.cmd` *once* from the extracted project. It clones your repository, copies the source, creates a commit, and pushes without force. It prompts for your GitHub login through Git Credential Manager if necessary. Do not share passwords or personal access tokens in chat.
4. Go to GitHub **Actions** and verify **Source checks** are green. Repository settings may require enabling Actions.
5. Run **Windows installer and release** → **Run workflow** manually first. This compiles a **test installer** and uploads an artifact under that workflow run, *not* a public release. Download it and test installation on your Windows PC.
6. Close the old v0.6.x folder application before installing the new one. Keep it as a backup until the installed v0.7 version launches correctly. Window placement settings should remain in your Windows user-data profile. Match entries saved through browser localStorage may not migrate if the application file location changes, so note important manually entered lineups first. Test before removing the old directory.

### Publishing the first actual release (when ready)

After checking the installer, create and push a Git tag `v0.7.0` that matches the `package.json` version exactly. For example, in a clone of the repository:

```
git tag v0.7.0
git push origin v0.7.0
```

The release workflow builds the NSIS installer, the update metadata (`latest.yml`) and the blockmap, and uploads them to a **draft** GitHub Release. Review the artifacts before manually clicking **Publish release** in GitHub. Only published releases are seen by the in-app updater.

For a subsequent version, update the source and `package.json` version (e.g. 0.7.1), push it to `main`, then tag `v0.7.1`. Repeat review and publish. No new local Windows build is necessary for users once they have the installed updater-enabled edition.

## Why not use the existing EXE folder?

Your working `Build-EXE-Folder.cmd` creates an unpacked desktop app without the NSIS installer/update manifest. v0.7 **disables the updater in unpacked builds** to avoid misleading errors; it still works for manual mode. For automatic updates use the installer generated by GitHub Actions.

## Release safety

- The app downloads updates only from the release feed embedded at build time for `awkwardcarl/deadlockcounteradvisor`.
- No GitHub access token is shipped to Windows users. CI uses GitHub's temporary `GITHUB_TOKEN` during tagged publishing only.
- **Public release warning:** The starter installer is unsigned. We strongly recommend obtaining a trusted Windows code-signing certificate and configuring secure signing before broad public distribution. GitHub-hosted files and hashes are useful but do not replace publisher identity verification.
- Updates are never installed without an explicit user click. The user should close their match before clicking **Install & restart**.
- Do not change repository owner/name after users install releases without planning a migration; an abandoned feed address could later be claimed by someone else.
- Overwolf game integration remains disconnected until appropriate approval.
- Do not disable Windows security protections merely to run or build this application.

## If the NSIS build fails

Inspect the GitHub Actions output. Previous local portable builds failed while extracting `winCodeSign` due to Windows symbolic-link privileges. The hosted Windows build is a separate environment, and the pipeline deliberately leaves `signAndEditExecutable` disabled. That may avoid the old issue, **but it is not verified until Actions builds and your Windows PC installs the result**.

## Workflow controls

- Every push to main runs static/source checks.
- A manual **Windows installer and release** run compiles but does **not publish**.
- Pushing a correctly versioned `v*` tag creates a *draft* release. Only you publish it after inspection.
